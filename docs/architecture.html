SynapX · Waypoint Logistics

System architecture & data model

Waypoint Logistics plans and delivers stock from two depots (Peliyagoda and Kandy) to 120 stores across three retail chains: Fresh, Style and Tech. Store managers order, dispatchers plan vehicles and routes, dock loaders load the trucks, and drivers deliver with proof of delivery. Everyone works in one web app, and every module reads and writes the same PostgreSQL database.

Live at synap-x-waypoint-logistics-8thu.vercel.app. Based on the dev branch (commit 615e274) and a read-only inspection of the Neon database at Alembic revision 0021_dock_arrival_pick, 4 October 2026.

1Main components

A browser front end, a Python API and a managed PostgreSQL database, with sign-in, file storage and email handled by dedicated services.

  • Next.js web appOne app with a separate area for each role. The /loader and /driver areas run offline and sync later.
  • FastAPI backendRouters validate the request, services apply the business rules (order cut-offs, vehicle capacity, route timing), and the ORM writes to the database.
  • Neon PostgreSQLThe single source of truth for all modules. The schema only changes through Alembic migrations, never from application code.
  • KeycloakHolds passwords and roles. The backend checks each token against Keycloak's public keys and uses its Admin API when an admin creates or changes a user.
  • Cloudflare R2 & emailPhotos go to R2 and only their link is saved. Emails are saved to an outbox table first, then a separate worker sends them.

2How an order moves through the system

Each module picks up the order from the database where the previous one left it. The order's status records how far it has got.

3Core data model

The tables that carry an order from placement to proof of delivery, and the foreign keys that connect them. Each line is a foreign key; the key column is listed in the table at the “many” end.

5How the data is stored and connected

  • One relational databaseAll modules share one PostgreSQL schema. 75 foreign keys tie them together, so the loader's checklist row points at the same orders row the store manager created.
  • Migrations onlyTables are created and changed only through Alembic (31 migrations, currently at 0021). The live Neon schema matches the code's models exactly.
  • Statuses are enumsOrder, run, stop and issue lifecycles are PostgreSQL enum types (26 in total), and the order service rejects any status change that isn't allowed.
  • Plans are snapshottedRoute plans are stored as JSON on allocations and dispatch_trips. run_stop_orders copies each order's units and weight when the plan is made. A later change creates a new plan_revisions version, and the loader must acknowledge it before releasing the truck.
  • Offline-safe writesThe loader tablet and driver phone give every action a unique client_action_id. A unique constraint means an action replayed after an outage is applied only once. Loader history is append-only (loading_checks, run_release_actions).
  • Identity is delegatedKeycloak owns credentials and roles, and users.keycloak_id links each account. Assignment tables limit what people see: a store manager sees one outlet, a dispatcher one depot. Loaders use a PIN on a registered tablet (loader_users).
  • Files live outside the databaseDelivery, SOS and issue photos are stored in Cloudflare R2. Only the link (photo_url) is kept in PostgreSQL.
  • Email can't get lostAn email is written to email_outbox in the same transaction as the event that caused it, with a unique event_key. The worker sends it and retries on failure.
  • Reference data from CSVOutlets, vehicles, the operating calendar and the three brand catalogues are loaded from CSV files by seed scripts. District travel times are read from CSV at run time.

6Hosting

The system is live at synap-x-waypoint-logistics-8thu.vercel.app.

  • Vercel hosts the Next.js web app and the FastAPI backend.
  • Neon hosts the PostgreSQL database.
  • Keycloak runs on its own hosted server.
  • Cloudflare R2 holds photos, because Vercel's serverless functions can't keep files between requests.
  • The email worker needs to run continuously, so it runs as a separate process outside Vercel.

The repository also has Docker images for the frontend and backend, with a docker compose setup that runs the whole stack on one machine with a local database.
